# Component patterns

Apply this document when creating, changing or reviewing Stencil components in
`packages/ui-components`. React-authored components follow their package's existing
layout and [React test guidance](../.agents/skills/react-tests/SKILL.md).

## Naming and rendering

Component directories use kebab-case without the `kv-` prefix; tags include it
(`components/badge/badge.tsx`, `tag: 'kv-badge'`). Components use Shadow DOM
(`shadow: true`). React consumers import the generated PascalCase binding, such as
`KvBadge`, from the public client entry.

Use one stylesheet with design-token CSS custom properties. Light and night themes
come from the body's `mode` attribute. Follow the [design-tokens skill](../.agents/skills/design-tokens/SKILL.md)
for token selection and generation; component-specific theme styles do not own theming.

## Component file structure

Each component follows a consistent structure in `packages/ui-components/src/components/[component-name]/`:

**Required Files:**

-   `[component-name].tsx` - Main component logic (StencilJS component)
-   `[component-name].types.ts` - TypeScript interfaces and enums
-   `readme.md` - Auto-generated documentation (generated by Stencil)

**Styling Files:**

-   `[component-name].scss` - Single stylesheet using CSS custom properties from design tokens

**Optional Files:**

-   `[component-name].config.ts` - Configuration constants
-   `[component-name].helper.ts` / `[component-name].utils.ts` - Helper functions
-   `test/[component-name].spec.tsx` - Unit tests (Jest)
-   `test/[component-name].e2e.ts` - E2E tests (Puppeteer)
-   `test/__snapshots__/` - Jest snapshots
-   `usage/react.md` - React-specific usage documentation

**Examples:**

Simple component (`badge/`):

```
badge/
├── badge.tsx
├── badge.types.ts
├── badge.scss
├── readme.md
└── usage/
    └── react.md
```

Complex component (`calendar/`):

```
calendar/
├── calendar.tsx
├── calendar.types.ts
├── calendar.scss
├── calendar.config.ts
├── calendar.helper.ts
├── readme.md
├── test/
│   ├── calendar.spec.tsx
│   ├── calendar.e2e.ts
│   └── __snapshots__/
└── usage/
    └── react.md
```

## Public exports and generated output

Stencil generates `readme.md` and React bindings through `reactOutputTarget` in
`stencil.config.ts`. Edit source contracts and regenerate these outputs.

Keep the explicit runtime enum exports in
`packages/react-ui-components/src/ui-components.ts` synchronized when adding or
removing a core enum. `export type *` does not expose a runtime enum value.

Changes to core source, types or enums require `pnpm build:packages` before React
consumers and Storybook can use them. Stencil can skip type checking when it writes
`src/components.d.ts`; run the core `typecheck` command after the build too.

## Storybook and API documentation

Put stories under `apps/react-storybook/src/components/<category>/<component-name>/`
with a PascalCase `<ComponentName>.stories.tsx` filename. Reuse the existing category
that owns the control and import interactive components through `/client`.

Use [API discovery](api-discovery.md) for supported CSS properties, icon contracts
and generated catalogs. Document public React props and callbacks at their source;
the catalog should describe their actual types and documented defaults.

## Creation and API-change workflow

1. Identify the existing component, public exports and Storybook category. Follow the design-tokens skill for token changes.
2. Update source and focused tests. Keep the React enum runtime bridge and affected callers consistent with the public contract.
3. Run `pnpm build:packages`, then `pnpm --filter @kelvininc/ui-components typecheck`. The build supplies Stencil metadata and React bindings before consumer validation.
4. Update the story and run affected unit/browser tests. Inspect the changed behavior and exposed states in Storybook.
5. Run `pnpm docs:generate` and `pnpm docs:check`. Review generated contracts with their source and report checks actually performed.
